# A blocked gesture climb no longer cancels itself

**Completed:** 2026-09-06 11:18:44 EDT (America/New_York)

## Prompt

Still not smooth, and it never has been. Stop adding switches.

## The bug

Two paths handle a blocked move, and they disagree.

Manual flight calls `stopManualMotion()`: velocity goes to zero, the pilot keeps
control, and the next frame tries again.

Gesture flight called `stopCommand()`, which clears `gestureMotion` outright.
The command was destroyed, not paused.

That matters because `detourAround` returns immediately when
`Math.hypot(local.x, local.y) < 0.00001`. A straight-up move has no horizontal
component, so there is no deflection to fall back on: **one blocked frame ended
a climb.** The held pose then only rebuilt it on the repeater's next 750 ms
tick, so the drone rose, stopped, rose, stopped.

It also explains why circling looked smooth. An orbit is horizontal, so a
blocked frame finds a lateral deflection and keeps moving.

## What changed

- `3d-mapping/src/drone-controller.ts` — a blocked gesture move now calls
  `stopManualMotion()` and marks the state `BLOCKED`, keeping `gestureMotion`
  alive. A later clear frame restores `GESTURE_CONTROL` and the climb carries
  on by itself.
- `3d-mapping/src/collision.ts` — holding in place exposed a second problem.
  The failed-route memo suppressed all probing for up to a second, so a drone
  that now waits rather than being cancelled did not notice the way clearing.
  While held up it re-checks the straight path every `FAILED_RETRY_SECONDS`
  (0.2 s) with a single query; the nine-query deflection search stays
  suppressed for the full second.

Also reverted, on request: the `?collision=off`, `?tiles=light` and `?score=`
switches added while diagnosing. Tile detail and classifier threshold are back
to their committed values.

## Verification

- `tsc --noEmit` + `vite build` clean. `npm test` 83/83 pass, including a new
  test, "a blocked gesture climb resumes itself instead of ending the command".
- **Mutation-checked.** Restoring `stopCommand()` on the blocked path fails
  that test and nothing else.
- One existing test changed contract. "a drone with no safe route stops
  re-searching every frame" asserted *zero* repeat queries while pinned. It now
  asserts one to four cheap re-checks over half a second, because a drone that
  waits in place has to notice when the obstruction goes. The expensive search
  is still suppressed.
- Measured against the pre-change sources, 10 s of held thumbs-up with the
  upward check tripping in short windows:

  | Obstruction | Before | After |
  | --- | --- | --- |
  | Five 250 ms blocks | 166 m, stalled 533 ms | 171 m, stalled 217 ms |
  | Eight 200 ms blocks | 161 m, stalled 767 ms | 165 m, stalled 433 ms |

## Notes and limitations

- Stall time roughly halves; it does not go to zero. A genuinely blocked climb
  still holds, which is correct. The remaining stall is the 0.2 s re-check
  interval plus however long the obstruction really lasts.
- Whether the upward check actually trips during the demo climb is not
  established from the running app. The defect is structural and was read from
  the code: a vertical move has no fallback, and the gesture path destroyed the
  command where the manual path preserves it.
- This is the fourth distinct fault found in the same held-gesture path, after
  the probe rate (`422bf96`), classifier dropouts (`13cb39c`), and stray hand
  shapes (`02cb883`).
