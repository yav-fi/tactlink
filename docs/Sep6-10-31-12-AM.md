# Held gesture commands survive classification dropouts

**Completed:** 2026-09-06 10:31:12 EDT (America/New_York)

## Prompt

The drone still jags on a held thumbs-up: it moves between about four distinct
vertical positions while climbing. Circling shows much less of it.

## The bug

The "four positions" and "circle is smoother" observations together identify it.

`orbit` runs `runLocalMission` with a 3600-second orbit step. It is issued once
and then runs on its own, so recognition after that point is irrelevant —
which is why circling looks smooth.

`takeoff` is a momentary command. `GestureCommandRepeater` keeps it alive only
while the recognizer keeps reporting the same source, with a 220 ms release
grace. MediaPipe's canned classifier drops below its score threshold regularly
even with the hand plainly in frame, and those failures cluster. Each cluster
longer than 220 ms produced `gesture_stop`, which calls `stopCommand()` and
halts the drone outright.

Recovery then cost the full hold again: `GestureHoldInterpreter` latches `fired`
to the gesture it last fired and clears it only after a rest, so the pose had to
be re-held for `GESTURE_HOLD_MS` (400 ms) before the drone moved again. About
620 ms of dead air per dropped classification. Over a few seconds of climbing
that is a handful of separate movement bursts — the four vertical positions.

There was also a latent deadlock. If the source changed because
`FingerMotionInterpreter` produced a label while `classified.gesture` stayed
`Thumb_Up`, the repeater cancelled but `fired` never cleared, so the command
could not restart until the operator lowered their hand.

## What changed

- `3d-mapping/src/gesture-repeat.ts` — `update` takes `handPresent`. A hand
  still in frame whose pose is momentarily unclassified now gets a 1200 ms
  grace instead of 220 ms. A hand that leaves the frame, or a different pose
  taking over, still stops on the original 220 ms.
- `3d-mapping/src/gesture-hold.ts` — new `rearm()`, which clears the latch so
  the pose currently being held can command again. Because `heldSince` is
  unchanged, an already-held pose resumes immediately rather than waiting out
  another 400 ms hold.
- `3d-mapping/src/gesture-camera.ts` — passes `result.landmarks.length > 0` as
  `handPresent`, and calls `interpreter.rearm()` whenever a `gesture_stop` is
  emitted.

Hand detection is far steadier than pose classification, which is what makes
`present` a better release signal than "the classifier is confident right now".

## Verification

- `tsc --noEmit` + `vite build` clean. `npm test` 80/80 pass, including two new
  tests:
  - "a hand still in frame keeps its held command through unclassified frames"
  - "a released command can be re-held without lowering the hand"
- **Mutation-checked.** Reducing the grace back to `RELEASE_GRACE_MS`
  unconditionally fails the first; making `rearm()` a no-op fails the second.
  All other tests passed under both mutations.
- Measured against the pre-change sources, 10 s of held thumbs-up at 16 fps
  recognition with clustered dropouts, hand in frame throughout:

  | Dropout | Before | After |
  | --- | --- | --- |
  | 15% | 170 m, 0 stops, 1 burst | 170 m, 0 stops, 1 burst |
  | 25% | 170 m, 0 stops, 1 burst | 170 m, 0 stops, 1 burst |
  | 35% | 155 m, 1 stop, 2 bursts | 170 m, 0 stops, 1 burst |
  | 50% | 124 m, 3 stops, 3 bursts | 170 m, 0 stops, 1 burst |
  | 65% | 119 m, 4 stops, **4 bursts** | 170 m, 0 stops, **1 burst** |

  The 65% row reproduces the reported four vertical positions and shows them
  gone.

## Notes and limitations

- An unclassified hand cannot hold a command open indefinitely: after 1200 ms
  the command still releases. That is the trade for surviving dropouts, and it
  means an operator whose hand is in frame but limp keeps climbing for up to
  1.2 s. Lowering the hand out of frame still stops within 220 ms.
- The dropout rates above are modelled, not measured from the real recognizer.
  The mechanism and the fix do not depend on the exact rate; the rate only sets
  where the old behaviour starts breaking down.
- This is a separate fault from the probe-rate stutter fixed in `422bf96`. That
  one was frame timing; this one stops the drone outright.

## Follow-up

- `FingerMotionInterpreter` can report `twoFingers`/`threeFingers` from a noisy
  landmark frame while the operator holds an unrelated pose. That now recovers
  automatically, but suppressing the spurious labels would be better.
