# Gesture input switch, flight smoothing, and smarter obstacle avoidance

**Completed:** 2026-09-06 07:59:38 EDT (America/New_York)

## Prompts

Two prompts, delivered together.

1. Add a button to the UI to toggle the gesture camera between the iPhone and
   the Mac, instead of hand-editing the `input` query parameter.
2. Fix the jittery drone animation while flying, and make automatic obstacle
   avoidance smooth and intelligent: it detected collisions but then bounced,
   got stuck inside building geometry, and threw the camera around as the drone
   jagged through the mesh.

## What changed

### Gesture input switch

- `3d-mapping/index.html` — a `nav#input-switch` in the bottom command dock,
  after the telemetry list. Two links: `?mode=local` (iPhone) and
  `?mode=local&input=camera` (Mac webcam).
- `3d-mapping/src/main.ts` — marks the active source with `aria-current="page"`.
- `3d-mapping/src/style.css` — segmented-control styling matching the existing
  telemetry cells, plus responsive column fixes (see Notes).

The switch navigates and reloads rather than swapping input live. `phoneMode` is
a module-level constant read in roughly ten places — camera handlers, deploy
altitude, HUD labels, the `phone-mode` body class, and which subsystem starts —
so live switching would mean tearing down and rebuilding the Cesium scene, the
phone poller, and the MediaPipe pipeline. Links also match the `.mode-switch`
nav that already exists for runtime-vs-local. The nav carries `local-only`, so
it is hidden in `?mode=runtime`.

### Obstacle avoidance (`3d-mapping/src/collision.ts`)

- **Failed-route memo.** A search that finds no way through records the origin
  and requested heading. While the drone has not moved (5 cm) or turned (1.8
  degrees), and for at most one simulated second, the result is reused instead
  of re-running the search. Previously a drone pinned against a wall spent nine
  building queries *every frame* — each one an offscreen pick pass with a GPU
  readback that stalls the frame it runs on. This is the main cause of the
  reported jagging.
- **Detour side hysteresis.** `MotionGuard` remembers which side a detour
  succeeded on and tries that side first next time. Previously the candidate
  order was fixed, so a drone could alternate sides as geometry came in and out
  of the ray and stall in front of an obstacle.
- **Wider detour angles.** `DETOUR_DEGREES` gains a 130-degree pair, letting the
  drone turn back along a wall it has reached instead of reporting no route.
- **Corridor shortening instead of invalidation.** A gradual turn now trims the
  cleared corridor to the distance over which the drift stays inside the swept
  ray width (`DRONE_CLEARANCE / sin θ`) rather than discarding the corridor and
  paying for a fresh probe. Re-probing still happens for reversals (`dot <= 0`).
- **Longer lookahead**, `LOOKAHEAD_SECONDS` 0.25 → 0.4. The whole corridor is
  swept by the ray, so this costs no accuracy; it only commits the drone further
  ahead of the last look at the map, still inside the 0.5 s corridor lifetime.

### Flight and camera smoothing

- `3d-mapping/src/drone-controller.ts` — travel direction is now blended toward
  the instantaneous direction with a weight of `moved / 0.5 m`, instead of being
  replaced by the raw per-frame position difference. Smoothing by distance
  rather than by frame count keeps the same flown path identical at any frame
  rate, and a near-reversal falls back to the new direction rather than
  normalizing a zero vector.
- `3d-mapping/src/main.ts` — the automatic camera blends heading at rate 1.1
  instead of 4.5 while the followed drone is avoiding or blocked, so a detour no
  longer whips the view around the obstacle.
- `3d-mapping/src/main.ts` — per-frame integration is clamped to 1/30 s instead
  of 0.1 s. A hitched frame now advances the world in slow motion rather than
  jumping a cruising drone metres in a single step.

## Notes and limitations

- **Responsive layout was checked by reading the CSS, not by measuring it in a
  browser** — there is no headless browser driver in this project. Three
  breakpoints were adjusted: `#local-command-dock` gained a third column,
  `.phone-mode` drops the 460 px minimum on the command column (the command
  input is hidden there anyway), and the `@media (max-width: 1100px)`
  `has-battery` rule gained a column so the switch stays on the telemetry row.
- The direction-blending change is the smallest of the three smoothing fixes.
  Everything downstream of `travelDirection` already damps — the model yaw
  through `smoothRenderedHeading` at rate 9, the camera through `blendHeading` —
  so the camera damping and the frame clamp do most of the visible work.
- No measurable heading noise was found in slow straight flight in the headless
  harness, so the rounding-noise motivation for distance-weighted blending is
  reasoning about precision, not an observed defect.
- The failed-route memo means a drone that is genuinely stuck stops searching
  and reports `BLOCKED`. It does not add an escape behaviour that would fly the
  drone out of geometry it is already embedded in; that would change commanded
  semantics, and the existing contract that a blocked descent must not become a
  climb is covered by a test.
- The two input modes do not share a gesture vocabulary. The Mac webcam runs the
  full set; the phone demo recognizes three poses. The switch changes what the
  operator's hands do, not just where the camera is.
