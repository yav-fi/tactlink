# Fix the stutter in gesture flight

**Completed:** 2026-09-06 09:58:40 EDT (America/New_York)

## Prompt

The drone bounces up and down while climbing on a held thumbs-up. Find the bug,
fix it, and remove the diagnostic overlay.

## The bug

`scene.pickFromRay` renders an offscreen pick pass over the whole Google
Photorealistic tileset and reads the result back from the GPU. It stalls the
frame it runs on, and on this machine that stall measured around 50 ms against a
median frame of 8.4 ms — roughly six dropped frames every time it runs.

`MotionGuard` cleared a corridor ahead of the drone and then flew inside it for
free, but the corridor was far too short-lived: `LOOKAHEAD_SECONDS` 0.4 with a
`CORRIDOR_MAX_SECONDS` lifetime of 0.5. In a straight 18 m/s climb that
re-probed roughly three times a second, and the live overlay showed four. Three
to four 50 ms freezes per second is the bouncing.

The corridor is swept by the ray over its whole length, so clearing a longer one
costs nothing in accuracy — it only commits the drone further ahead of its last
look at the map, and the corridor is still abandoned the moment the drone turns
out of it.

## What changed

- `3d-mapping/src/collision.ts` — `LOOKAHEAD_SECONDS` 0.4 → 2.5,
  `MAX_LOOKAHEAD_METERS` 30 → 45, `CORRIDOR_MAX_SECONDS` 0.5 → 3.
- `3d-mapping/src/gesture-camera.ts`, `3d-mapping/src/gesture-worker.ts` (new) —
  recognition moved off the render thread. `recognizeForVideo` needs an
  `HTMLVideoElement`, which a worker cannot have, so the main thread transfers an
  `ImageBitmap` per frame and the worker returns landmarks and gesture scores.
  Interpretation (holds, finger motion, command repeats) stays on the main
  thread, where it is already covered by tests. One frame in flight at a time;
  newer frames drop rather than queue.
- `3d-mapping/src/gesture-camera.ts` — the recognizer ran on `delegate: "CPU"`,
  which measured about 60 ms per inference. It now prefers `"GPU"` (25–35 ms
  measured) and falls back to CPU if creation fails.

Fallbacks, since this is the demo path: worker creation failure, a missing
`Worker`/`createImageBitmap`, or a model load over 15 s all fall back to
recognizing in the page. `?gesture=inline` and `?delegate=cpu` force the old
paths for comparison.

## Verification

- `tsc --noEmit` + `vite build` clean. `npm test` 78/78 pass.
- Measured with a harness loading `fleet` from the pre-change sources and from
  the working tree, 600 frames at 1/60 s:

  | Scenario | Building queries/s before | after |
  | --- | --- | --- |
  | Held thumbs-up climb, clear sky | 2.7 | 0.5 |
  | Manual forward flight, clear sky | 2.7 | 0.7 |

  At the ~50 ms per query observed in the browser, that is about 135 ms/s of
  frozen frames during a climb down to about 25 ms/s.
- Live overlay readings that led here, from the machine running the demo:
  frame p50 8.4 ms with p95 62.1 ms while climbing, and p50 8.3 ms with p95
  63.2 ms while hovering with zero collision queries. The hover reading is what
  ruled out the avoidance system as the sole cause and pointed at recognition;
  moving recognition to the worker took p95 to 50 ms, and the residual was the
  probe rate.

## Notes and limitations

- The remaining worst case is unfixed: a genuinely blocked path can try nine
  deflections in one frame, which is roughly a third of a second of frozen
  picture. Spreading that search across frames was implemented and reverted
  because it broke the single-call semantics that five existing tests rely on
  (one `moveManually` call is expected to settle to `collisionBlocked`). It
  needs those tests reworked alongside it. The failed-route memo already stops
  that search from repeating every frame.
- Longer corridors trade a bounded amount of staleness for far fewer probes. The
  ray verifies the full corridor when it is cast; the exposure is geometry that
  streams in during the up-to-three seconds afterwards.
- The worker adds roughly one frame of gesture latency, well inside the 400 ms
  hold.
- The diagnostic overlay used to find this is removed. It measured frame time
  percentiles, recognition cost, tile streaming, and attributed slow frames.
  Worth rebuilding if this recurs.

## Follow-up

- Rework the five avoidance tests so the deflection search can be spread across
  frames, removing the last long freeze.
- A cheap CPU broad-phase before the GPU pick would cut probes further; the
  corridor is currently the only thing standing between flight and a pick.
